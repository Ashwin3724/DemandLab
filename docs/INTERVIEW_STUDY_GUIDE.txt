DEMANDLAB — BEGINNER INTERVIEW STUDY GUIDE

This guide reflects the AI-assisted DemandLab code. It uses fictional data and an illustrative stock rule; it is not a production inventory tool. Do not claim real demand accuracy, cost savings or independent authorship without evidence. Read, test and modify the code yourself.

1. THE PROBLEM

A time series is a set of observations ordered in time. Demand forecasting predicts future units from earlier observations. An organization might want to avoid both excess stock and stockouts, but a forecast alone does not decide how much to buy: current inventory, lead time, constraints, uncertainty and costs also matter.

DemandLab generates a fictional daily sales series, compares two forecasting approaches on earlier validation windows, reports one later test, predicts the next seven days, and illustrates a simplistic stock total. It also accepts a fictional daily CSV. Its outputs are for learning, not business decisions.

2. FORECASTING BASICS

Trend is a longer-term direction or changing level. Seasonality is a repeating pattern, such as weekdays vs weekends. Noise is variation not explained by the simple pattern. The synthetic generator creates all of these using invented formulas and random noise. Real demand can be affected by promotion, prices, holidays, stockouts, competitors and changing customer behavior, none of which are modeled here.

A horizon is how far ahead a forecast goes. DemandLab forecasts seven daily steps. A point forecast is one numeric estimate; it does not express the full range of plausible outcomes.

3. DATA, LAGS AND THE BASELINE

A lag is a past value used as a feature. Lag 1 is yesterday, lag 7 is seven days ago, lag 28 is 28 days ago. A rolling mean over the previous seven days summarizes recent level. These are computed using only history available before the predicted day.

The baseline is seasonal naive: tomorrow's estimate is the value seven days before it. For a seven-day forecast, it repeats the latest observed week's pattern. A baseline matters because a complicated model should justify itself against a simple, relevant alternative.

4. RANDOM FOREST FORECASTING

A decision tree predicts by applying learned split rules to inputs. A random forest averages predictions from multiple trees. DemandLab fits a RandomForestRegressor using lag 1, 7, 14 and 28, the previous seven-day mean and weekday. It uses 60 trees, min_samples_leaf 4, and a fixed seed.

This is a tabular ML model applied to time series, not a special neural forecasting model. It is refitted using only the history available at each backtest origin. It may struggle with trend extrapolation, new conditions and unusual values outside the training examples.

5. RECURSIVE SEVEN-DAY PREDICTION

For day one, features come from the observed history. For day two, the previous prediction is now part of the history; subsequent predictions feed later features. This is recursive forecasting. It avoids accidentally feeding the true future demand into predictions, but errors can compound over the horizon.

Alternative strategies include direct models per horizon or models that output several horizons at once; those are NOT implemented here. A good comparison evaluates them on the same realistic test windows.

6. ROLLING-ORIGIN BACKTESTING AND LEAKAGE

A backtest re-creates a past decision: fit on data available up to an origin, predict the next period, and compare with what actually happened. DemandLab uses three non-overlapping seven-day validation windows. Each later window can legitimately use data that occurred before its origin, including observations from earlier windows, because those values would then be historical. The final seven days are held out for test during selection.

Data leakage means using information unavailable at the prediction time. For example, building day-one features from the actual sales of day two would leak future information. The code generates forecast inputs recursively. Models are fit using training history only for each origin; the final test does not choose the model. The developer nevertheless inspected test results, so it is not an independent final benchmark.

7. EVALUATION METRICS

Absolute error for one day = |actual - forecast|.
MAE = average absolute error across the evaluated days, in the same units as demand. If actual values are [10, 20] and forecasts [12, 17], absolute errors are 2 and 3; MAE is 2.5 units. This is an illustrative calculation, not a project result.

WAPE = sum of absolute errors / sum of actuals. It is undefined if actual total is zero. DemandLab calculates test WAPE but displays test MAE. Both metrics hide some detail: inspect by horizon, product and period, and consider business consequences. A lower error on the generated validation data does not prove a model will work in a real store.

8. INTERVALS AND STOCK ILLUSTRATION

The built-in sample displays forecast ± the 90th percentile of absolute validation residuals for the selected model, clipped at zero on the low side. This is a simple empirical error margin, NOT a calibrated prediction interval, and no 90% coverage is established. Only 21 validation predictions contribute to the margin. It does not account for different uncertainty at different horizons.

Uploaded CSV forecasts do not show this interval because a margin from synthetic validation data should not be assumed valid for a different series. The upload workflow uses the model choice from the synthetic experiment and fits it to the uploaded history; the model choice itself has not been validated on that series.

The stock number shown equals sum of seven daily forecasts × 1.10. It ignores stock on hand, lead time, holding/stockout costs and other constraints. It is explicitly an illustration and not a real reorder recommendation.

9. APPLICATION ARCHITECTURE

app/forecast.py creates data, validates CSV, builds lag features, trains models, performs backtests and computes forecasts. app/main.py exposes FastAPI endpoints. app/static/ holds the browser UI. run.py installs dependencies on first run and opens a loopback server. Python packages and initial setup require internet, but no API key or cloud service is required afterward.

CSV requirements: UTF-8, date and sales columns, at least 60 and at most 2,000 unique consecutive daily rows, finite nonnegative numeric sales, and max 2 MB. User uploads may temporarily be written to disk by the multipart parser. Do not use sensitive data. This local server has no login and must not be exposed publicly.

10. INTERVIEW QUESTIONS

Q1 What problem is solved? A: Demonstrates time-aware daily forecasting and an illustrative stock calculation on a synthetic series.
Q2 What is a time series? A: Observations ordered over time; the ordering matters because future information must not leak backward.
Q3 What is seasonal naive? A: Reusing the value from the corresponding previous seasonal period, here seven days earlier.
Q4 What is a lag feature? A: A prior observed or, during recursion, predicted value at a specified offset.
Q5 Why compare a baseline? A: A more complex model must justify itself against a simple relevant method.
Q6 How is the forest trained? A: On historic lag and weekday features with a scikit-learn random forest regressor.
Q7 What does recursive prediction mean? A: Earlier forecasts become input to later forecast steps; errors may compound.
Q8 What is rolling-origin backtesting? A: Repeatedly fit on data before an origin and score predictions for the following period.
Q9 How does the code avoid future leakage? A: Each window fits only on earlier history; future features use model predictions rather than actual future sales.
Q10 How is the model selected? A: Lowest mean absolute error over three validation windows.
Q11 How is MAE calculated? A: Average absolute difference between actual and predicted units.
Q12 Does the displayed range guarantee 90% coverage? A: No. It is an empirical residual margin on only 21 synthetic validation points, not calibrated.
Q13 What happens for an uploaded CSV? A: Fit the selected method to its history, return seven predictions, and omit the synthetic-derived uncertainty range.
Q14 Is the stock figure production-ready? A: No. It ignores inventory, lead times, costs and constraints.
Q15 How many real customers were served? A: None established; the delivered example uses synthetic data.
Q16 What is your contribution? A: Explain honestly that initial code was AI-assisted, then describe concrete code changes, tests and experiments you performed.

11. LEARNING EXERCISES

Read generate(), design(), fit_forest(), predict() and experiment() in app/forecast.py. Trace a single forecast day and verify that it cannot see a later true value. Calculate MAE by hand and compare with metrics(). Upload the fictional example and verify no interval is shown. Deliberately omit a day from a copy and verify the CSV is rejected. Add a unit test for another malformed input. Design an experiment comparing different forecast horizons on genuinely held-out data; do not invent measured improvements.
